# SACTCheck development and release workflow

## Current delivery preference — manual ZIP

- The user has returned to the original manual delivery workflow. Prepare and validate changes in the existing checkout, then provide a ZIP containing the update files, a copyable GitHub commit summary and description, and concise audit/review evidence.
- Do not commit, push, merge, create a pull request, or deploy unless the user explicitly requests that action for a future task. General requests to complete a batch or update the site use manual delivery by default.
- The publication steps below describe how to verify a separately authorized publication; they do not override this manual-delivery preference. Clearly distinguish a locally validated review package from a deployed release, and retain every blocked or unverified check.

## Repository and version

- Use the existing checkout. Cloud tasks are already isolated; do not create a Git worktree unless requested.
- Preserve existing user changes and instructions. Read nested `AGENTS.md` files before changing their directories; append new guidance without discarding existing requirements.
- At the start of release work, inspect `git status`, fetch `origin main`, and report the full remote commit SHA and its `package.json` version. Compare local HEAD with that commit before updating anything. Do not reset, overwrite, or invent a requested version that is absent remotely.
- Derive the active release from `package.json` and the canonical release module; derive protocol and patient counts from their current indexes/registry. Historical README text, versioned filenames, cached build output, and previous task reports are not evidence of the current release.

## Local development and validation

- The static application has no npm dependencies. Use the Node major specified by the current CI workflow when available; report a different tested runtime. Do not introduce dependency manifests or lockfiles merely for setup.
- Run `npm run build:pages` and `npm run security:site`, then serve `_site` with `python3 -m http.server 8000 --bind 127.0.0.1 --directory _site`. Confirm HTTP content, not just a process or port. Compare the served release and protocol index with the selected checkout; select patient routes from its current registry.
- Run the current `npm run test:ci` for release validation; inspect its definition and current release-specific scripts so newly added suites are included. Distinguish passing, failing, skipped, and unrun checks. Diagnose historical test/selector failures without disabling assertions.
- During environment setup, keep application source, tests, manifests, lockfiles, and tracked generated assets unchanged. Some tests and generators rewrite tracked reports, HTML, JSON, and PDFs. Run them in a fresh disposable copy outside the checkout (excluding `.git` and `_site`) and keep logs/results there. During an actual requested release, generate required assets intentionally, inspect every diff, and commit the intended outputs.
- Keep TLS, signatures, and checksum verification enabled. Use inherited platform Git/proxy authentication; do not ask for tokens merely because a CLI prompts for login. Never put secret values in documentation, logs, or chat.

## Mobile, PDFs, QR codes, and visual evidence

- Exercise the affected clinician and patient journeys in a real browser at narrow mobile and desktop widths, including navigation, tabs, forms, expandable content, urgent-help links, and PDF downloads. Check overflow, clipping, readable text, visible controls, console errors, and failed local assets. Inspect screenshots; a successful build or browser launch is insufficient.
- Check iPhone/Safari and Android/Chrome Add to Home Screen instructions, the manifest, saved-icon destination, and treatment-specific QR routes. Chromium emulation does not establish real Safari, Android installation, camera scanning, or device printing behavior. Report untested device checks explicitly.
- Use the existing release's PDF generators and verifiers, discovered from the current tools and release scope. Generate a representative PDF, inspect its rendered pages, and validate page count, text retention, bounds, print sizing, and equality of published/compatibility copies. Run the full affected release PDF checks before release.
- Decode QR PNGs and QRs rasterized from PDFs; compare exact destinations with the intended regimen and canonical HTTPS route. Check that those deployed destinations respond correctly. Creating an image or finding a QR filename is not QR validation.
- Managed-cloud authoring tools are installed separately at `/workspace/.sactcheck-tools/venv` with pinned requirements in `/workspace/.sactcheck-tools/python-requirements.txt`. They provide WeasyPrint, PyMuPDF, Pillow, qrcode, zxing-cpp, and lxml for handbook generation and verification. Node Playwright and `/usr/bin/chromium` support local visual checks. Confirm availability in each restored environment and use the saved environment install instructions when needed. Do not assume live processes survive restoration.

## Complete a requested release

1. Establish the requested scope and verified baseline, implement the authorized changes, and update release metadata and affected generated assets consistently.
2. Run repository/release validation, PDF and QR checks, and mobile/desktop functional and visual checks. Inspect the final diff and retain useful results. Report blockers and repository defects; do not label a mobile release ready based only on a local build.
3. Prepare a concise commit summary and description explaining the concrete behavior change, validation, and remaining limitations. Commit the intended changes and push to the authorized release branch. Continue these steps as part of a requested release without repeatedly asking for permission already given. Never force-push or change unrelated branches to overcome an access problem.
4. Verify the GitHub Actions run for the exact pushed SHA, including the Pages deployment job, using existing authenticated access. A successful Git push proves neither Actions API permission nor deployment success. The current Pages workflow deploys pushes to `main`; a setup or feature branch does not deploy automatically.
5. After deployment succeeds, fetch the canonical deployed release module and representative pages/assets/PDFs; compare them with the release artefacts and test the QR destinations. Check for stale cached content. Report the pushed SHA, release version, deployment result, and any remaining mobile/device limits.
6. If Git write access, required checks, Actions status, canonical-site access, or device validation is unavailable, identify the precise missing capability and mark the corresponding stage blocked or unverified. Do not claim end-to-end release readiness.

The temporary onboarding write-access test alone does not authorize changes to `main`. An explicit user request to merge into `main` or perform a release authorizes that requested work, including the resulting deployment verification.

## Clinical batch scope and preservation

- For each requested batch, verify the backlog against current main and record the five outstanding context suites and five repeat clinical audits, their selection rationale, and the baseline commit. Distinguish outstanding colorectal contexts of existing shared regimens from entirely new regimens. If no ordered retrospective queue exists, identify the proposed scope as a proposal; missing progress metadata does not establish that a regimen has never been audited.
- Obtain the current official NCCP sources before declaring a clinical audit complete. Record source URLs, document versions, dates, SHA-256 hashes, page/table citations, and any uncertainty. Retained older PDFs can support a historical comparison but do not establish current source validity when retrieval is blocked.
- Audit source-specific clinical decision thresholds and component-specific actions, including baseline versus treatment-day eligibility, organ function, toxicity grades, recovery, recurrence, dose history and hold/stop decisions. Keep clinician assessment, knowledge/evidence, consent, monitoring, supportive care and patient content consistent. Never fill unavailable criteria or unsupported clinical claims from a generic template.
- Preserve detailed anatomical toxicity illustrations and their explanatory text, the three-page patient pack, front/back wallet cards and print dimensions, regimen-specific QR destinations, and complete printable handbooks with all applicable support sheets. Do not replace rich anatomical material with a shortened summary to make layout or tests pass.
- Compare affected HTML and rendered PDFs with the previous release: text retention, anatomy, page count, bounds, readable contrast, card dimensions, QR decoding and destination, mirrored download copies and complete handbook sections. Inspect representative mobile/desktop screenshots and PDF pages, and provide review links with the commit summary and description.
- Run clinical source-boundary, software, browser, PDF, QR and visual regressions. In an environment with Playwright and Chromium, run `CHROMIUM_PATH=/usr/bin/chromium npm run test:patient-browser` alongside the current `test:ci`. Update stale browser tests to current documented behavior with explicit expectations; preserve meaningful coverage and do not skip assertions or reinstate intentionally retired clinical UI merely to make a test pass.
- If a required source audit or check is blocked, commit and push only validated independent work to a development branch, record completed versus blocked stages, and do not merge it into main. Do not mark blocked backlog items complete or describe a development branch as a production release. A production release requires exact-commit deployment and live-asset verification; identify every unverified stage. Independent clinical, oncology-pharmacy and patient/PPI review remains a separate requirement.

## UI refresh and print preservation

- Timeline wording must come from each authored regimen/phase row, never a global pump-duration label. Run `npm run patient:ui` after intentional patient-content generation, then `node tools/refresh-patient-ui.cjs --check`. This refreshes only recognized fragments and accessible support markup; preserve and report specialized timelines and unrelated drift.
- Keep responsive screen consent/support layouts separate from A4 print styles. Every risk, medicine/timing column, field and signature must remain available. Modal dialogs must manage initial focus, Tab/Shift+Tab, inert background, Escape and focus restoration, including asynchronous transitions.
- Keep a concise evaluation/privacy warning visible, with its full explanation accessible. Early task navigation and progressive disclosure must retain all original clinical paragraphs, lists, source links and detailed anatomical illustrations. Provide Expand all and restore complete print content.
- For a UI-only handbook refresh, use `tools/build-patient-handbooks-v08433.py --routes all --reference-only --report <new-report-path>` with the scoped PDF Python environment. Preserve the existing six non-reference handbook sections, three-page guide, wallet sheet and support sheets. Keep chart labels/bars together, repeat the day-axis on continuation, and use an unambiguous global handbook folio. Legacy v08431/v08432 builders overwrite shared print styling and must not be used for this refresh.
- Refresh existing consent PDFs with `tools/render-consent-pdfs.py --report <new-report-path>`; it stages and validates one-page A4, complete text, bounds, caption colors and mirrored copies before publishing any output. Do not relax content checks to accept a renderer/font mismatch.
- Run `npm run test:patient-ui`, `CHROMIUM_PATH=/usr/bin/chromium npm run test:patient-browser`, and the scoped environment's `python tests/handbook-chronology-print.test.py`, alongside current software/PDF/QR regressions. Compare changed screenshots and PDFs with the previous commit, record before/after hashes for intended asset migrations, and prove clinical data and retained anatomy/pack sections unchanged before updating protected-asset fixtures.
- The UI migration regression verifies baseline Git blobs as well as current hashes. Keep full-history checkout enabled for CI/Pages, run the UI gate before building the deployment artefact, and do not skip provenance assertions in shallow clones.

## Context completion, patient packs and the overall MVP gate

- Reconcile a batch against current encoded indications and context-specific services. Report declared historical completion flags, actual context coverage and required output availability separately. A shared regimen's completed breast/lung service does not establish a colorectal service, and an earlier audit remains an earlier audit. Do not increment completion for blocked or partly delivered contexts.
- Maintain a consistency matrix for every affected context: assessment decisions and units, clinician knowledge/evidence, consent, monitoring, supportive care, patient portal/passport, three-page guide, wallet card, full handbook, shared templates and source versions. Mark current-source verification and unresolved attribution separately from historical metadata and successful software probes.
- Before overall MVP completion, perform and record a full cross-platform consistency audit across **every tumour group**, covering clinician and patient journeys, shared components, clinical differences, source versions, web/mobile presentation, PDFs and QR destinations. A standard presentation must preserve regimen-specific clinical differences; a ten-context batch is not this global audit.
- Preserve the approved patient pack structure: page 1 gives schedule, phases/modalities, required tests and between-cycle expectations; page 2 gives detailed regimen-specific anatomical toxicity anchoring and explanations; page 3 gives front/back wallet panels, appropriate cycle tracking, cutting instructions, automatic regimen QR, contacts/resources and webapp instructions. Clearly label placeholder contacts and preserve the detailed anatomical illustrations. Complete handbooks must provide a logical offline reading sequence containing all essential information.
- Resolve renderer/font differences before replacing a PDF with changed pagination. Record renderer/library versions, explicit per-document font files and hashes, and the stylesheet profile. Share the same font configuration between CSS parsing and PDF rendering. Compare retained text, word geometry/page bounds, anatomy, wallet dimensions, mirrors and decoded image/PDF QRs; do not globally substitute one font profile across documents with different established profiles or remove content to recover a page count.
- Create a new dated recovery package outside the checkout before batch changes, preserving the initial commit, refs, source archive, Git history, patches/untracked inventory and verified checksums. Never overwrite older backups. A snapshot on the same cloud filesystem is not separately protected offline storage; state explicitly whether an independent offline copy was made.
